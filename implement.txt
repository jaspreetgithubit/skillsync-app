# 3. Feature 2: Individual Student–Project Compatibility

## Objective

Implement an intelligent compatibility engine that evaluates how suitable an individual student's profile is for a particular project.

For example:

A student has the following skills:

- JavaScript
- React
- Node.js
- MongoDB
- Docker
- PostgreSQL

A project requires:

**Mandatory skills:**
- React
- Node.js
- Python
- Machine Learning

**Preferred skills:**
- MongoDB
- Docker

The compatibility engine should compare the student's confirmed profile against the project's structured requirements and calculate an explainable compatibility score.

The system should clearly communicate:

1. How well the student matches the project.
2. Which required skills are matched.
3. Which required skills are missing.
4. Which preferred skills the student possesses.
5. Which skills are only partially related, if applicable.
6. Why the student received the calculated score.
7. Whether the student satisfies the project's critical skill requirements.

The system must not simply generate a random percentage or ask an LLM to guess a compatibility score.

The score must be calculated using a consistent, testable, and explainable algorithm.

# 4. Accuracy Requirement — IMPORTANT

My academic project requires the compatibility system to achieve **more than 90% accuracy**.

Treat this as a measurable engineering and evaluation requirement.

However, never fabricate accuracy results. Do not claim that the system achieves more than 90% accuracy merely because the scoring function works or the tests pass.

### Define accuracy correctly

Create a labelled evaluation dataset containing student–project pairs reviewed by humans.

Each pair should have a ground-truth label:

- `RELEVANT`: The student is a suitable match for the project.
- `NOT_RELEVANT`: The student is not a suitable match for the project.

Use these human-reviewed labels to evaluate the system's final classification.

The numeric compatibility score should be converted into a classification using a configurable threshold.

For example:

- Score at or above the threshold: `RELEVANT`
- Score below the threshold: `NOT_RELEVANT`

The threshold must be calibrated using the validation dataset, not chosen by looking at the test results.

### Evaluation methodology

Implement an evaluation workflow with:

- A representative labelled dataset, preferably containing at least 200 student–project pairs.
- Training or development data, validation data, and an independent held-out test dataset.
- A split strategy that reduces leakage from repeated students or projects across datasets.
- Accuracy calculation.
- Precision calculation.
- Recall calculation.
- F1-score calculation.
- Confusion matrix.
- Classification threshold evaluation.

The core objective is:

**Held-out test accuracy greater than 90%.**

Also evaluate precision, recall, and F1-score so that a highly imbalanced dataset does not create a misleading accuracy result.

### Critical evaluation rules

1. Do not use synthetic or automatically generated labels as proof of real-world accuracy.
2. Do not evaluate the system using the same examples used to tune its weights and threshold.
3. Do not hardcode an accuracy value such as 95% in the application.
4. Do not modify the test labels to improve the results.
5. If the available human-labelled dataset is insufficient, clearly report that the 90% target has not yet been verified.
6. Provide a simple process for adding more human-reviewed examples and rerunning the evaluation.
7. Keep test results reproducible and document the dataset size, split strategy, threshold, and evaluation date.

If the initial algorithm does not achieve the target, investigate the errors and improve the algorithm using the validation dataset. Do not claim success until the independent test evaluation supports it.

**Remember: the compatibility percentage shown to users is a suitability score, not a statistical accuracy percentage or a probability of project success.**

# 5. Skill Normalization and Matching Engine

This is one of the most important parts of the implementation.

Students and projects may describe the same technology differently.

For example:

| Student skill | Project requirement | Expected treatment |
|---|---|---|
| React.js | React | Equivalent |
| NodeJS | Node.js | Equivalent |
| JS | JavaScript | Equivalent |
| PostgreSQL | Postgres | Equivalent |
| Mongo | MongoDB | Equivalent |
| Python 3 | Python | Equivalent |

Implement a centralized skill normalization service.

### A. Canonical skill names

Maintain a consistent representation of technical skills.

For example:

- React.js → React
- ReactJS → React
- NodeJS → Node.js
- JS → JavaScript
- TS → TypeScript
- PostgreSQL → PostgreSQL
- Postgres → PostgreSQL

The normalized skill should be used by the scoring engine, APIs, and frontend.

### B. Avoid incorrect equivalences

Do not treat related technologies as identical.

For example:

- Java ≠ JavaScript
- React ≠ React Native
- Node.js ≠ Java
- HTML ≠ JavaScript
- MongoDB ≠ PostgreSQL
- Machine Learning ≠ Deep Learning

False-positive skill matches must be treated as a serious quality issue.

### C. Semantic skill matching

Exact and trusted alias matching should be the primary matching mechanism.

For genuinely ambiguous or related skills, you may use semantic similarity or an existing AI/embedding integration.

However:

- Semantic similarity must not automatically turn unrelated technologies into equivalent skills.
- A semantic match must not receive the same score as an exact canonical match unless it is an approved equivalent.
- Use conservative similarity thresholds.
- Keep the semantic matching mechanism configurable.
- Record why a partial match was identified.
- Do not make external AI calls for every skill comparison unnecessarily.

If the existing AI provider abstraction from Feature 1 can be reused, use it where appropriate. Do not duplicate provider configuration or expose API keys in the frontend.

The core compatibility algorithm must continue to work even when an external AI provider is unavailable.

# 6. Compatibility Scoring Algorithm

Implement the scoring engine as a separate, reusable backend service.

Do not place the scoring algorithm directly inside React components or Express route handlers.

The algorithm must be deterministic: identical student profiles and project requirements must produce identical results.

### A. Project requirement structure

Each project's skills should have structured requirements.

A suggested structure is:

```json
{
  "requirements": {
    "skills": [
      {
        "name": "React",
        "priority": "required",
        "weight": 5,
        "critical": true,
        "minimumProficiency": "intermediate"
      },
      {
        "name": "Node.js",
        "priority": "required",
        "weight": 4,
        "critical": false
      },
      {
        "name": "Docker",
        "priority": "preferred",
        "weight": 2,
        "critical": false
      }
    ]
  }
}
```

This is an illustrative structure. Adapt it to the existing project model rather than blindly replacing existing fields.

Validate requirement data when projects are created or updated.

Each skill requirement should support:

- Skill name
- Priority: required or preferred
- Importance weight
- Optional critical flag
- Optional minimum proficiency

Allow the existing project creation/editing workflow to capture structured skill requirements if it does not already do so.

### B. Recommended scoring approach

Use a configurable weighted scoring approach.

As an initial default, consider:

| Component | Default weight |
|---|---:|
| Required skill coverage | 70% |
| Preferred skill coverage | 20% |
| Proficiency fit | 10% |

These weights must be configurable and documented.

Do not artificially award points for skills unrelated to the project.

Calculate each component separately.

**Required skill coverage:** Evaluate how well the student satisfies mandatory skills, taking their individual importance weights into account.

**Preferred skill coverage:** Evaluate how many preferred skills the student possesses, also considering importance weights.

**Proficiency fit:** Evaluate whether the student's explicitly recorded proficiency satisfies the project's expected proficiency.

If proficiency information is missing, treat it as unknown. Do not automatically assume that the student is either a beginner or an expert. Exclude unavailable proficiency information from the calculation and appropriately redistribute the applicable component weight.

If a project has no preferred skills, handle that situation correctly without producing division-by-zero errors or artificially lowering the student's score.

### C. Skill match strengths

Use a consistent matching-strength model.

For example:

- Exact canonical match: full match.
- Trusted alias match: full match after canonicalization.
- Approved related-skill match: partial credit according to its configured strength.
- Unverified semantic suggestion: do not automatically award full credit.
- No match: zero credit.

The strength values should be centralized in configuration rather than scattered throughout the code.

### D. Critical requirements

A project may have specific skills marked as critical.

If a student does not possess a critical skill:

- Clearly identify that missing requirement.
- Set a separate `criticalRequirementsSatisfied` or equivalent result.
- Explain the impact on project suitability.
- Do not hide the missing requirement behind a high overall percentage.

The compatibility score and eligibility status must be independently understandable.

### E. Final result

Return a structured result containing:

```json
{
  "score": 82.5,
  "classification": "RELEVANT",
  "criticalRequirementsSatisfied": false,
  "breakdown": {
    "requiredSkillCoverage": 80,
    "preferredSkillCoverage": 100,
    "proficiencyFit": 75
  },
  "matchedSkills": [],
  "missingRequiredSkills": [],
  "matchedPreferredSkills": [],
  "partialMatches": [],
  "explanation": "..."
}
```

This is an example response contract, not a requirement to return these exact scores.

Use real calculated results.

The score, classification, and eligibility status must have clear and consistent meanings throughout the application.

# 7. Explanation and Transparency

An important requirement is that students should understand why the system recommends or does not recommend a project.

Do not simply display:

"Your compatibility score is 82%."

Instead, communicate the reasons.

For example:

**Compatibility: 82.5%**

- Matched skills: React, Node.js, MongoDB.
- Missing required skills: Python, Machine Learning.
- Matched preferred skills: Docker.
- Critical requirement status: Not satisfied.
- Proficiency mismatch: React proficiency is below the project's requested level.

Provide a concise explanation generated from the actual scoring result.

The explanation must be grounded in the structured result. Do not let an LLM invent missing skills, experience, or achievements.

The explanation can use deterministic templates. An LLM may improve the wording if appropriate, but it must never change the underlying score or matching result.
